# Единые интенты, промпты и сущности: подключение к сценарию

## Проблема

Интенты и промпты задаются в двух местах: в словаре проекта и во вкладках сценария. В схеме это nullable `scenario_id` у `intents` и `prompts`: `NULL` — объект словаря, иначе — объект сценария. Один и тот же объект редактируется в двух местах, неясно, где главное.

## Решение

Объекты всегда проектные. Сценарий не владеет ими, а подключает их. Всё, что зависит от сценария, хранится на подключении (как уже сделано для `scenario_entities.required`).

## 1. Данные

- Новая `scenario_intents(id, scenario_id, intent_id, is_global, position)`, уникальность `(scenario_id, intent_id)`, каскадное удаление по обеим сторонам.
- Новая `scenario_prompts(id, scenario_id, prompt_id, position)`, уникальность `(scenario_id, prompt_id)`.
- `intents`, `prompts`: колонки `scenario_id` нет в новой схеме. `scenario_steps.any_intent` тоже нет.
- В уже существующих БД (хранятся в браузере) старые колонки физически остаются: SQLite не умеет удалять колонку с внешним ключом без пересоздания таблицы, а пересоздание рискует каскадным удалением. Миграция обнуляет `intents.scenario_id` и `prompts.scenario_id` (иначе удаление сценария каскадно удалило бы интенты), код эти колонки больше не читает и не пишет.
- `scenario_entities` без изменений. `intent_entities.required` без изменений: это обязательность слота внутри интента, а обязательность сущности для сценария по-прежнему `scenario_entities.required`.
- Строки `scenario_steps` получают третий вид: `kind = 'global'` (рядом с `transition` и `error`). Это переход глобального интента из любого состояния. `state` у такой строки пустой, `next_states` — состояние-цель в той же вкладке сценария, ответ ассистента и действие системы берутся из состояния-цели, как у обычных переходов.
- Строка ошибки без интента (`intent_id IS NULL`) означает «по любому интенту».

### Миграция существующих данных (`PRAGMA user_version` 0 → 1)

1. Интент/промпт с заполненным `scenario_id` подключается к этому сценарию; `scenario_id` обнуляется.
2. Любой интент/промпт, на который ссылаются `scenario_steps` или `scenario_states` сценария, подключается к этому сценарию.
3. Объект без использований и без `scenario_id` остаётся проектным и ни к чему не подключённым.
4. Строки `kind = 'transition'` с `any_intent = 1` переводятся в `kind = 'error'`; затем `any_intent` обнуляется.

Миграция выполняется при открытии БД. Старые дампы проекта (`project-dump.ts`) апгрейдятся при импорте по тем же правилам; устаревшие поля в дампах игнорируются.

## 2. Семантика глобального интента

- Подключение с `is_global = 1`: интент срабатывает в любом состоянии сценария. Его переходы — строки `kind = 'global'`, их может быть несколько (с условиями, порядок = приоритет).
- Подключение с `is_global = 0`: интент срабатывает только в состояниях, указанных в строках переходов.
- Флаг на подключении: один интент может быть глобальным в одном сценарии и локальным в другом.
- Подключениями управляют отдельные запросы, а не `PUT /scenarios/:id`:
  - `POST /scenarios/:sid/intents` — создать интент и сразу подключить;
  - `PUT /scenarios/:sid/intents/:iid` `{ is_global }` — подключить существующий / сменить флаг;
  - `DELETE /scenarios/:sid/intents/:iid` — отключить.
  То же для промптов (без флага).
- `PUT /scenarios/:id` сам подключает всё, на что ссылаются сохраняемые строки и состояния (если подключения ещё нет), и отвергает глобальный переход, чей интент не подключён как глобальный.
- Снять глобальность или отключить интент/промпт, на который в сценарии ещё есть ссылки, нельзя: ответ `409 in_use`. Сначала убирают ссылки.

## 3. Интерфейс

- Вкладка «Интенты» сценария: таблица подключённых интентов (имя, фразы, сущности, переключатель «Глобальный»). «Добавить» — выбрать из проекта или создать новый (попадает в словарь и сразу подключается). «Убрать» снимает подключение, объект остаётся. Правка идёт прямо в таблице.
- Вкладка «Промпты»: то же без «Глобальный».
- Сущности сценария: выбрать из словаря или «Создать новую» (попадает в словарь). Обязательность и follow-up prompt задаются в сценарии (как сейчас).
- Выбор интента/промпта в шаге и состоянии: только из подключённых.
- Блок «Глобальные переходы» на вкладке «Логика»: переходы глобальных интентов, без выбора исходного состояния.
- Словарь: список без группировки по сценариям (группы «Подключены к сценариям» / «Не используются»), в карточке «Используется в» со ссылками на сценарии. Удаление объекта, подключённого к сценариям, предупреждает об этом.
- У интента/промпта, подключённого более чем к одному сценарию, в таблице сценария пометка «также в N сценариях»: правка меняет его везде.
- Удаление сценария удаляет только его подключения; интенты и промпты остаются в словаре.

## 4. Экспорт, импорт, готовность

- Экспорт сценария строится по подключениям (`scenario_intents`, `scenario_prompts`), а не по ссылкам из шагов.
- Раздел «Глобальные переходы» появляется перед «Переходами между состояниями», только если глобальные переходы есть; в таблицах состояний они не повторяются. Колонки: «В состояние», «Запрос пользователя», «Условия», «Действие системы», «Ответ ассистента». При нескольких вкладках — подзаголовок с именем вкладки.
- В строках ошибок без интента колонка «Запрос пользователя» показывает «Любой интент сценария».
- `project-dump.ts`: добавляются таблицы `scenario_intents`, `scenario_prompts`; устаревшие поля пропускаются; старые дампы апгрейдятся.
- `demo.ts` без `any_intent`; критерий «сценарий готов» в `routes/projects.ts` считает подключённые интенты/промпты.

## 5. Тесты

В `core/test`: миграция (все случаи использования + `any_intent`), подключение/отключение/смена флага, 409 при ссылках, глобальный и локальный интент в экспорте, удаление объекта и сценария, готовность сценария, апгрейд старого дампа. В `web`: `analyzeSteps` игнорирует глобальные строки.

## Вне рамок

Откат миграции; копирование интента вместо подключения; визуализация глобальных переходов на графе состояний.
