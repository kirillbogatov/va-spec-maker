# CUI Spec Maker — дизайн

Дата: 2026-10-17. Обновлено 2026-10-19: модель и экспорт приведены к формату документа «L3 New Format».

## Цель

Локальный веб-сервис для описания и генерации спецификаций сценариев голосового помощника. Разделы: Интенты, Сущности, Промпты, Сценарии. Экспорт спецификации проекта в DOCX (формат L3) и MD. Поддержка нескольких проектов.

## Решения

- Хранение: SQLite (файл `data/spec.db`), доступ через локальный сервер. Старые базы мигрируют автоматически при открытии (`migrate` в `server/src/db.ts`).
- Стек: Vite + React + Shadcn UI + Tailwind (web), Express + better-sqlite3 (server). Один репозиторий, `npm run dev` запускает оба процесса; в production Express отдаёт собранный фронтенд на одном порту.
- Дизайн: минималистичный, монохромная палитра, один акцентный цвет, шрифт Inter, без теней.
- Экспорт: DOCX (библиотека `docx`) и Markdown, генерация на сервере из одних и тех же табличных определений (`export/tables.ts`).
- Несколько проектов: у каждого свои интенты, сущности, промпты, сценарии.
- Формат переходов: из двух вариантов документа (Transition table и Transition table (alternative)) выбран основной. Он содержит колонку Next states и описывает автомат состояний целиком, а в альтернативном нет Next states, зато ответ VA зависит от VoiceOver. Условие VoiceOver можно записать в поле Condition.

Вне объёма (YAGNI): правила классификации, токены и переменные, рассылки, аналитика, авторизация, тестирование NLU.

## Модель данных

- `projects` — id, name, description.
- `entities` — project_id, name, description (служебное), `multiple_values`, `followup_prompt`. Имя уникально в проекте.
- `entity_values` — value (каноническое значение), synonyms (JSON-массив).
- `intents` — project_id, name, group_name, enabled, comment. Группа и комментарий служебные, в документ не попадают.
- `relative_adjustments` — справочник проекта: name, description. Интенты выбирают значения из него.
- `intent_variants` — единственная строка таблицы Intents интента (один интент — один вариант); колонка `relative_adjustment` устарела и после миграции пуста.
- `variant_adjustments` — relative adjustments интента: adjustment_id (справочник), `examples` (JSON-массив примеров запросов), position.
- `variant_phrases` — тренировочные фразы варианта.
- `variant_entities` — сущности варианта: entity_id, `required`.
- `prompts` — name, `full_answer`, `short_answers` (JSON-массив).
- `scenarios` — именованная группа строк (организационная, в документ не попадает).
- `scenario_dependencies` — зависимости сценария (параметры и проверки при запуске): `ref` (стабильный ключ), `entity_id` либо собственное `name`, `type` (`string` / `enum` / `bool`), `options` (варианты для `enum`). У строки `scenario_steps` есть `conditions` — список пар «зависимость (`ref`) — значение»; они выводятся в колонке Condition вместе со свободным текстом, а таблица зависимостей — в разделе Dependencies экспорта.
- `scenario_steps` — строка Transition table или Errors: `kind` (`transition` / `error`), `state`, intent_id + `request_params` (User request), `condition`, `system_action`, `next_states`, prompt_id (VA response). Порядок колонок в таблицах и выгрузке: State, User request, Condition, System action, Next states, VA response. Для `transition` строка — ребро схемы (см. «Сценарии»), `next_states` содержит одно состояние.
- `scenarios.layout` — JSON `{состояние: {x, y}}`: положение узлов схемы, в том числе узлов без рёбер. Только раскладка, на экспорт не влияет; узлы без записи раскладываются автоматически слоями от входа.

Каскадное удаление: проект удаляет всё своё содержимое. Удаление сущности, используемой в интентах, требует подтверждения с перечнем интентов (привязки удаляются). Удаление интента или промпта оставляет строки сценариев без интента/промпта.

## Экраны

Каркас: сверху переключатель проектов (с созданием) и кнопка «Экспорт» (DOCX / MD); слева сайдбар с разделами Интенты, Сущности, Relative adjustments, Промпты, Сценарии.

### Интенты
Слева: поиск, список по группам, счётчик фраз. Справа редактор: название, переключатель «Вкл», группа, комментарий, затем таблица Relative adjustments (значение из справочника + примеры запросов), Entities (выбор сущности + required), Тренировочные фразы (ввод по Enter, массовая вставка, поиск, массовое удаление). Автосохранение.

### Relative adjustments
Слева список, справа: название, описание, список интентов, где используется. Удаление используемого значения убирает его (с примерами) из интентов.

### Сущности
Слева список, справа: название (в документе `[name]`), Multiple values allowed, Follow-up prompt, таблица значений (значение + синонимы, массовая вставка `значение: синоним1, синоним2`), список интентов, где используется.

### Промпты
Слева список, справа: название, Full answer, Short answer (несколько вариантов).

### Сценарии
Слева список сценариев. Справа — зависимости, схема переходов и таблица Errors.

**Схема переходов — источник данных для Transition table.** Сценарий — конечный автомат: узел — состояние, ребро — одна строка перехода «состояние + интент + условия → одно следующее состояние». Из одного состояния по одному интенту можно уйти в разные состояния в зависимости от условий — это отдельные рёбра (параллельные рёбра между одной парой узлов тоже допустимы). Развилок как отдельных узлов нет.

- Редактирование: ребро создаётся протягиванием от узла к узлу; узел создаётся кнопкой или двойным кликом по полотну и переименовывается на месте. Выбор узла или ребра открывает боковую панель. Панель ребра: интент, параметры запроса, условия (те же `ConditionsCell`), ответ ассистента, действие системы, порядок. Панель узла: имя, «Сделать входом», упорядоченный список исходящих рёбер (порядок = приоритет проверки условий, меняется стрелками). Подпись ребра — интент и условия кратко.
- Первое состояние — вход (отмечается явно). Конечные состояния — узлы без исходящих рёбер, в том числе служебные слова END, EXIT…
- Раскладка: координаты узлов хранятся в `scenarios.layout`; пока их нет, действует авторасстановка слоями от входа. Кнопка «Разложить заново».
- Таблица для экспорта строится из схемы: при сохранении строки упорядочиваются обходом в ширину от входа, внутри состояния — по порядку рёбер, затем недостижимые состояния. Готовый вид показывает вкладка «Предпросмотр».
- Проверки (подсвечиваются на схеме и в предпросмотре): недостижимое состояние; ребро без следующего состояния; пустое ребро (нет ответа, действия и цели); недетерминизм — у одной пары «состояние + интент» несколько рёбер, и у двух из них одинаковые условия или у ребра без условий есть соседи после него (оно перекрывает остальные); состояние без исходящих переходов (предупреждение).

Хранение: ребро — строка `scenario_steps` (`kind = transition`), `state` — источник, `next_states` — ровно одно состояние. Порядок рёбер — `position`. Старые строки с несколькими значениями в `next_states` при первом открытии разбиваются на отдельные рёбра с копиями остальных полей; рёбра можно склеить обратно только вручную, экспорт не склеивает. Таблица Errors остаётся обычной таблицей с перетаскиванием строк, на схеме её нет (ошибки не привязаны к конкретному состоянию). Новая строка Errors наследует State предыдущей.

## Экспорт

`GET /api/projects/:id/export?format=docx|md`. Документ повторяет L3: разделы **Intents**, **Entities**, **Prompts** (с пояснением про VA responses), **Transition table** (с пояснением про колонки), **Errors**.

- Intents: Intent / Relative adjustment / Example requests / Training phrases / Entities. Одна строка на интент, примеры запросов сгруппированы по relative adjustment, фразы и сущности нумерованы, обязательные сущности помечены `(required)`, пустой relative adjustment выводится как `none`.
- Entities: `[name]`, значения маркированным списком «**Каноническое:** "синоним", …», `yes`/`no`, follow-up prompt.
- Prompts: Prompt / Full answer / Short answer (нумерованный список).
- Transitions: колонка Result code берётся из состояния, в которое ведёт переход (код результата хранится в состоянии сценария).
- Transition table и Errors: строки всех сценариев проекта, пустые ячейки выводятся как `-`.
- DOCX: альбомная A4, Arial, таблицы с чёрной рамкой, жирная шапка, ширины колонок как в эталоне. Название проекта хранится в свойствах документа и в имени файла.

## Ошибки

Сервер возвращает JSON `{error, message}`. Клиент показывает тосты (Sonner). Пустые названия и дубли имён проверяются на клиенте и сервере. Любое удаление требует подтверждения в диалоге.

## Тесты

Vitest: серверные роуты на SQLite в памяти, миграция старой базы, генераторы экспорта (структура MD, XML DOCX). UI проверяется вручную.
